> 2026-11-03 ｜ 前置：`README.md`（第一层采集+索引）。本文记录 A 的落地与**两轮精度修正**。

## 验证状态

**已实测**：616 会话打标（2 秒内）；实体覆盖 **78%**、意图覆盖 **59%**；
按 (实体×意图) 聚合、按实体列时间线均跑通；28 条测试；抽验修正后的误判（见 §四）。
**未验证**：B（演变时间线）未做；意图覆盖率 59% 是**刻意取舍**（宁缺毋滥），未做召回补全。

## 一、实体归并：必须做

实测（`tools/mine_entities.py`，按**会话数**统计裸名）：

| 名字 | 会话数 | |
|---|---|---|
| demo-wiki | **307** | 旧名 |
| demo-base | **27** | 新名 |
| demo-next | 94 | 又一层名字 |
| demo-kb | 56 | 中文名 |

合并后「demo-kb」= **353 会话（57%）**。若不合，同一件事会被拆成四条话题线。

**反向发现**：路径挖掘不可靠（`F:\xxx` 候选最高只 7 会话），会话正文更多用裸名。
→ 实体靠「种子词 + 同义词表」，用 `mine_entities.py` 定期核对发现新名字。

**注意**：归并只改**标签**，不改原文。会话标题里出现 `demo-wiki` 是历史原文，
归属标签已经是「demo-kb」——原文不能改写。

## 二、意图：固定清单（19 个），规则匹配，不用 LLM

理由：LLM 自由打标无法复核，且会产出"看起来对"的标签。固定标签可用测试钉住。

**纪律：意图关键词里不得出现实体名**（`codex`/`workbuddy`/`pageindex`…）。
实体名一出现就给意图加分 = 同一件事算两次（实测 `codex` 让「agent 协作」虚高到 129 会话）。
这条已写成测试（`test_no_entity_name_inside_intent_keywords`）。

## 三、两轮精度修正（都是量出来才发现的）

### 第一轮：关键词太泛

| 问题 | 现象 | 修法 |
|---|---|---|
| 子串匹配 | `ui`/`api` 命中 `build`/`requirement`/`capital`，「接口与前端」330 会话登顶 | ASCII 短词改**词边界** |
| 标识符 | `session` 命中 `session_key`、`token` 命中 `token_count` | 边界排除集加**下划线** |
| 裸词太泛 | `api` 单独覆盖 281 会话（46%） | 换具体词：`api 设计`/`restful`/`端点` |
| 万能词 | `服务`、`对比` | 换 `服务启动`/`方案对比` |

并把 5 个粗标签（>25%）拆细：文档解析→文档解析/OCR/分块/大纲目录树；
数值抽取→字段抽取/投标数值；会话上下文→上下文压缩/会话记录；
agent 协作→多agent委派/外部复核；接口前端→服务端接口/Web前端。

### 第二轮：泛词跨越领域（用户抽验发现）

抽验「16G内存可用14.2G是否被虚拟占用」时发现它被打了「字段抽取」「合规与风险」「部署与性能」。
逐词查上下文：

| 误判词 | 原文语境 | 实际含义 |
|---|---|---|
| 字段 ×3 | "SMBIOS 规范里只有「内存阵列最大容量」这一个**字段**" | **硬件字段**，不是抽取字段 |
| 风险 ×2 | "改坏内存时序的**风险**"、"补充一句**风险**提示" | **硬件风险**，不是合规风险 |
| 性能 ×1 | "任务管理器 → **性能** → 内存" | 界面标签 |

**根因**：2 字泛词在完全不同的领域里都会出现，阈值拦不住。**必须短语化**：

- `字段` → `字段抽取|字段归属|字段错|字段归一|抽取字段`
- `风险`/`安全`/`权限` → `合规风险|法律风险|废标风险|安全漏洞|权限控制|越权`
- `性能` → `性能瓶颈|性能下降|性能测试`

再叠加**命中强度规则**：
- 泛词（<4 字）需命中 **≥2 次**；
- 具体词（≥4 字 / 含空格或连字符）命中 **1 次**即可；
- 实体需 ≥2 次才算主话题（top 3，避免"提一句就算"），独苗实体兜底保留。

修正效果（同一会话）：

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 意图标签 | 字段抽取 / 合规与风险 / 部署与性能 | **（无）** |
| 实体 | 7 个（含只提一句的） | 1 个（Ollama，hits=3） |

## 五、归属信号升级：工具路径 > 正文提及（2026-11-03）

### 问题（用户抽验发现）

「建 `F:\agent-memory` 的那个会话」在话题视图里被归成「demo-kb」，
用户问："现在在讨论 F:\agent-memory，怎么会有 demo-wiki 的话题进来呢？"

追溯后确认是**两个不同问题**：
1. **实体归并是生效的**：会话标题里的 `demo-wiki` 是历史原文（不改原文），
   其归属标签已经是「demo-kb」。
2. **但归属本身不够硬**：原来只看"正文提及"，而那个会话 cwd 是 `F:\demo-kb`、
   正文大量讨论 demo-base 的检索 —— 于是被归成demo-kb。

### 三个信号实测对比

| 信号 | 可靠性 | 反例 |
|---|---|---|
| 正文提及 | 低 | 会话为背景介绍大量提及别的项目 |
| **cwd** | **低** | `F:\demo-main` 有 244 个会话（DSH 早期默认工作区），与话题无关 |
| **工具调用碰过的路径** | **高** | 直接是"动过哪些文件" |

### 做法

1. 采集器额外抽出**项目目录**（只存目录名与次数，不存工具输出）：
   - DSH `data.arguments`（JSON 串）、Codex `payload.arguments`、Claude `input` dict、
     Hermes 导出 md 的 `## Tool calls` JSON 块；
   - 结构化字段（`file_path`/`path`/`cwd`）+ **绝对路径正则兜底**（路径常塞在 `cmd`/`prompt` 里）。
2. 路径压成项目目录（显式分段，不用正则 —— 可选段会贪婪多吃一层）：
   `F:\agent-memory\collectors\base.py` → `f:\agent-memory`；
   `C:\Users\demo\Desktop\某项目\a.py` → `c:\users\demo\desktop\某项目`。
3. 目录名命中 `ENTITIES` 别名 → 用 canonical（`demo-wiki` → demo-kb）；
   否则目录名本身当实体（`agent-memory`）。公共容器丢弃（`dp`/`tmp`/`docs`/用户主目录根）。
4. 打标时**路径优先，正文兜底**（`label_session_scored(texts, tool_dirs)`）。

### 修掉的脏数据（都是实测出来的）

| 脏值 | 根因 | 修法 |
|---|---|---|
| `f:\demo-wiki;` | 路径写在句子里带分号 | 剥尾部标点 |
| `f:\demo-wiki，python` | 中文标点被吃进路径 | 在中文标点处截断 |
| `f:\demo-wiki/work/slices/...` | 路径用正斜杠，按反斜杠分段失败 | 先归一化分隔符 |
| `...示例客户B区...5.6.doc` | 第 4 段是文件名却当目录 | 有扩展名就不当目录 |
| **`demo`（56 会话）** | `c:\users\demo` 用户主目录根被当项目 | 用户主目录根判噪音 |

### 效果

- 有工具路径的会话比例：**DSH 88% / Codex 55% / Claude 36% / Hermes 少量**
- 实体覆盖 **81%**（498/618）；`demo-kb 359` 现在主要来自**路径**而非正文提及 ——
  含义从"提到过"变成"在这里干过活"，可信度更高。
- 那个 agent-memory 会话现在正确带上双实体：
  `实体=['demo-kb'(1013 次), 'agent-memory'(183 次)]`
  —— 它确实两头都干了（先做完 demo-base 的活再去建 agent-memory），**双实体是诚实结果**。

**注意**：这不是 bug 修复带来的"更准"，而是**换了更硬的判据**，
所以历史标签会小幅变化（Codex 97→88、Ollama 112→51 等），属预期。
