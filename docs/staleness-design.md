# 「讨论已失效甚至起反作用」的判定：调研 + GLM 评审 + 修正后的设计

> 2026-11-03 ｜ 前置：`docs/topics-a.md`、`docs/timeline-b.md`。
> 本文记录：外部调研结论、GLM-5.3 独立评审、以及**被评审推翻的我自己一个判断**。

## 验证状态

**已实测**：项目「demo-kb」359 会话 / 3173 条结论的分类统计；幽灵路径 58 条已逐个核对存在性。
**已评审**：GLM-5.3（非同源）读全部设计与实测数据，交 17 条意见（1 根本性错误 / 7 值得改 / 4 过度设计 / 5 待确认）。
**未验证**：三路路径判定（别名重指向后重验）的真实命中率尚未跑——这决定 🔴 的真实规模，**当前写不出准确数字**。

## 一、外部调研：别人怎么处理"知识失效"

| 来源 | 核心机制 | 对本项目的可用性 |
|---|---|---|
| **Zep / Graphiti**（[docs](https://help.getzep.com/facts.md)） | 事实（边）带四时间戳 `created_at/valid_at/invalid_at/expired_at`，双时态做 point-in-time 查询 | 机制可用；但官方明说**时间字段不代表事实为真**，且它只做**语义**失效，**不做前提校验** |
| **阿里云工程文**（[撤回清单+版本水位](https://developer.aliyun.com/article/1752786)） | 区分「删除文件」与「撤回证据」；`can_cite()` 要求「未撤回 **AND** 索引已追上水位」；**物理保留与引用资格是两套规则** | **最实用**，三件可迁移（见 §三） |
| **PACMI**（arXiv 2610.05732） | provenance-aware **级联失效** | 本项目**不做**（见 §二 Q2） |
| **TOKI**（arXiv 2606.06240） | 双时态算子代数做矛盾消解 | **过度设计**（只需两个时间字段） |
| **MemGuard**（arXiv 2608.21867） | verifier 信号持久化 | 无 LLM 可持久化信号，**过度设计** |

## 二、GLM 评审的关键结论

### 🔴 E1（根本性错误）：我把「探测时刻的状态」等同于「前提失效」

我原方案：路径不存在 ⇒ 标 🔴「该结论基于已不存在的 X，勿照做」。

**评审指出的错**：那 58 条里绝大部分是**项目迁移**（`F:\demo-wiki` → `F:\demo-base`）。
迁移意味着前提**换了名字活着**，不是死了 —— 该结论在新位置**可能仍然成立**。
打「勿照做」是**把仍有效的经验错误劝阻**，后来者会重踩一遍坑，**与本项目目标直接相反**。

同类语义错误：
- **端口**「无监听」探测的是**存活**不是**存在**——服务没启动是常态，此时探测会误标。
- **模型**「不存在」对历史实测类结论不构成失效（为真于当时），且模型没了就无人能照做，**危险度最低**。
- **口径**：88 是「有可验证前提」的数量，**不是失效数量**。原文把它当失效规模写，是错的。

### 其它必须改的（节选）

| # | 问题 | 修法 |
|---|---|---|
| W1 | 「没有后续会话推翻」存在**空真**：别的 agent 昨天的推翻句可能还没入库 | 加**索引水位**：断言前要求同话题更晚会话已全部入库 |
| W2 | 「文本仍显得权威（肯定语气）」**不可计算** | 删「语气」，只留机械特征（具体路径/端口/数值） |
| W3 | 两套 `verified` 概念冲突（timeline 的"自述实测" vs 处置档的"前提已验证"） | 改名区分，并写明三档期望分布 |
| W4 | `verified` 关键词没过自家探针纪律（「跑通」在「跑不通/你说实测过」里误命中） | 跑一次标记词抽验 |
| **W5** | **注入策略缺失** —— 🟡 3085 条不可能全注，"隔离"没有生效面 | 定次序：**跨 agent 交叉印证 > 新近 > 单源** |
| W6 | L4「只能人工」过于绝对 | 裁决人工，但**候选可机械生成**（假设漂移分诊） |
| W7 | L1 判定**无时间性** | 带 `check_at`，注入时**懒检验** |

### 过度设计（采纳）

- **L3 项目迁移层冗余** → 并入 L1 之前做**路径改写预处理**
- **TOKI 双时态代数** → 只需 `created_at` + `check_at`
- **PACMI 级联失效** → 不做（理由见 Q2）
- **MemGuard verifier 持久化** → 无信号可存

### Q3：我漏掉的三种"反作用"（评审补充，我认为都成立）

1. **适用范围错配**：三条件全过，但结论属于**另一个项目**（实体覆盖仅 81%，已有多实体会话被误归的真实案例）
2. **矛盾对**：两条互相冲突的结论无裁决地同时注入，**比不注入更糟**
3. **verified 腐烂**：实测类结论本身会过期（费率/行为变更），却没有前提可验 ⇒ **永久通过三条件** —— 判据缺**老化项**

### Q2：级联失效不做是对的，而且可以更硬

实测「同键多值 = 0」说明「结论→结论」的引用边建不起来；
**更硬的一刀**：即便那 3% 有前提的结论，其前提也是**路径/端口/模型（外部世界对象）**，不是别的结论
⇒ 连「前提→结论」之外的边型都不存在。L1 本身就是**退化的单跳级联**，且是唯一存在的边型。

## 三、修正后的设计

### 3.1 L1 改为三路路径判定（这是防误杀的关键）

| 判定 | 条件 | 处置 |
|---|---|---|
| `alive` | 路径存在 | 🟢/🟡 |
| **`dead-with-successor`** | 旧路径失效，但**别名表能重指向新位置**且新位置验证通过 | **🟡 带注**「路径已迁移至 X」，**不标勿照做** |
| `dead-no-successor` | 失效且无后继 | 🔴 真失效 |

别名表直接复用 `topics.py` 的 `ENTITIES`（`demo-wiki → demo-kb` 已落地）。
端口改为**配置级检查**（启动脚本 / `.env` / compose），不做瞬时探测；模型类**不进失效判定**。

### 3.2 状态三档改名（避免与 timeline 的 verified 冲突）

| 档 | 名字 | 含义 |
|---|---|---|
| 🔴 | `invalid` | 前提确证失效且无后继 |
| 🟡 | `unverified` | 无可验证前提（97%）或未发现失效 |
| 🟢 | **`cross-checked`** | **≥2 个 agent 独立出现过同一结论**（不看语气，看交叉印证） |

### 3.3 注入策略（W5，评审认为这是最缺的一块）

次序：**跨 agent 交叉印证数 > 新近 > 单源**；
**矛盾对不注入**（同话题两条冲突且无时间裁决 → 都不注入，只提示"存在冲突"）；
verified 类带 `recheck_after`（默认 90 天），过期降 🟡（补老化项）。

### 3.4 迁移自阿里云的三件（评审认可）

1. **双条件引用资格**：`未撤回 AND 索引已追上水位` → 直接补 W1 空真
2. **Tombstone 原因类型学**：L1 前提失效 / L2 显式推翻 / L4 语义过时
3. **物理保留 vs 引用资格分离**：与我们「不删只标」一致，显式成文

**不适用两件**：版本阶梯（会话是 append-only，无版本概念，只能用「入库批次/结束时间」弱替代）；
撤回的权威性（阿里云的撤回是源系统权威信号，我们的「改为」只是**证据级**，只能降权不能裁决）。

## 五、P0 / P1 / P2

**P0**：L1 三路路径判定（别名重指向 + 重验）—— 这是真正防"反作用"且**不误杀迁移结论**的一步。
**P1**：注入策略（交叉印证加权 / 矛盾对不注入 / 老化项）。
**P2**：L4 候选机械分诊（假设漂移候选交人裁）。

## 七、P0 实测结果：真 🔴 从 58 收敛到 **2**

实现：`premises.py`（三路判定）+ `cli.py premises <实体>`。实测项目「demo-kb」359 会话 / 3173 结论：

| 判定 | 数量 | 占比 | 处置 |
|---|---|---|---|
| 🟢 `alive` | **33** | 1.0% | 前提通过 |
| 🟡 `dead_with_successor` | **40** | 1.3% | 项目已迁移，**带注不劝退** |
| 🔴 `dead_no_successor` | **2** | 0.1% | 真失效 |
| ⚪ `unverified` | **3098** | 97.6% | 无可验证前提 / 非项目资产 / 乱码 |

### 收敛路径（每次缩减都是**修判据**，不是放宽阈值）

| 阶段 | 数量 | 修了什么 |
|---|---|---|
| 最初（前提：`os.path.exists` 即失效） | **58** | —— |
| ① 迁移重指向（评审 E1） | 40 🟡 + 14 | 项目迁移 ⇒ 前提换名活着，不是死了 |
| ② 系统/临时目录不算资产；`demo-system` 别名回退 | 6 | `C:\Windows\evil.txt` 是**攻击载荷**、`Temp\probe.py` 是一次性脚本 |
| ③ markdown 链接截断；通配符路径 | 4 | `[x.md](F:\demo-main\...)（含 15 行）` 抽出脏路径；`int-0*.json` 被截成 `int-0` |
| ④ GBK 乱码伪路径 | 3 | `F:\閿欒鎺掓煡\work` 是"讨论编码问题"的文本，不是路径 |
| ⑤ 乱码目录被当成"新实体" | **2** | `entities_from_paths` 会把乱码当新项目返回非空 entity，须按 pdir 是否 ASCII 判 |

### 最后这 2 条都是真的

1. `D:\demo-wiki-backup-20260617`（2026-06-16）—— 结论说"随时可回退到备份"，**备份目录已不存在**
2. `F:\CAD2025\`（2026-10-28）—— AutoCAD 卸载后目录消失，结论"本机 AutoCAD 不可用"仍成立，但引用路径失效

**⚠️ 这个结果本身就是最重要的结论**：
原本被我判为"高危 58 条"的集合，**真实规模是 2 条**。如果不做三路判定就把它们标成"勿照做"，
会**误伤 40 条仍有效的迁移经验 + 十几条无关路径**——正是 GLM 评审 E1 预言的问题。
