# 明天要细化的三件事

> 当前状态：`616 会话 / 34,795 条` 已入库，`cli.py search` 可用（2~7ms）。
> 第一层（采集+索引+检索）完成并已提交；下面是第二层的待定项。

## 1. 先定路线：话题归并 vs 演变时间线

- **A 话题归并**：实体词典 + 意图标签，把 `demo-base` / `demo-wiki` / `demo-next` / `demo-kb`
  认成同一实体，把「预算/交付/检索/评测/会话上限…」打上意图。
  → 不做这步，时间线会把同一件事拆成四条线。
- **B 演变时间线**：同一 (实体 × 意图) 按时间排 + 结论冲突检测 + `active/superseded/experiment` 状态。

**建议顺序：先 A 后 B**（A 是 B 的前提）。

## 2. 归一化要拍板的三个口径

1. **实体同义词表从哪来**：手写词典，还是从会话里抽（`F:\demo-base`、`F:\demo-kb`、
   `F:\demo-next`、`F:\demo-wiki` 这几个路径在会话里共现，可自动挖）？
2. **意图标签用固定清单还是开放**：固定 8~12 个（预算/交付/质保/保证金/检索质量/评测/会话上限/架构），
   还是让 LLM 自由打标再归并？（后者容易"看起来对"）
3. **结论冲突怎么判**：同一问题两个不同答案 → 标"后者可能推翻前者"，还是只按时间取最新？

## 3. 一个已知的偏差，别用错

**Hermes 71 个会话只入库 788 条正文**（其他 agent 上万），因为它导出的 assistant 纯文本常为空、
多轮靠工具调用推进。
→ 做话题热度/权重时**不能按消息条数等权**，否则 Hermes 会被系统性低估。
