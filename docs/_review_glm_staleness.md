# 设计评审：「讨论/调研已失效甚至起反作用」的判定设计

> 评审对象：`docs/_brief_glm_staleness.md`
> 依据材料：该 brief + 本仓 `docs/design.md`、`docs/topics-a.md`、`docs/timeline-b.md`、`docs/next.md`、`docs/example-timeline-pageindex.md`。
> 纪律遵守：未执行任何命令、未改任何代码；仅读文件与写本报告。需要材料之外信息才能判断的均标「待确认」。
> 条目计数：根本性错误 1 ＋ 值得改 7 ＋ 过度设计 4 ＋ 待确认 5 ＝ **17 条**，另附文档末尾 5 问的直接回答。

## 总评

骨架抓对了：承认 97% 无可验证前提 ⇒ 只机械做 3% 那一层、其余标「未验证」靠人，加上「不删但隔离」——这与你自己调研里的最好实践（阿里云「物理保留与引用资格分离」）一致，天花板承认得很诚实。**主要问题集中在一处**：被你标为「机械可信」的 L1 层，其**判定语义**（而非探测动作）并不成立，且恰好在实测数据的主流场景（迁移幽灵路径）上失效。其余是判据闭合性、口径一致性和「隔离之后注入什么」的缺口。

## 一、根本性错误（1 条）

### E1. L1 把「探测时刻的状态」直接等同于「前提失效」——三种探测各有语义漏洞

L1 的探测（路径不存在 / 端口无监听 / 模型不存在）是机械的，但「⇒ 前提失效」这个判定不成立：

- **路径（最严重，占 L1 主体）**：材料自述 76 条引用路径中 58 条（70%）是**项目迁移**留下的幽灵（`F:\demo-wiki`→demo-base 等）。迁移意味着前提**换了名字活着**，不是死了。对这 58 条打 🔴「该结论基于已不存在的 X，勿照做」：前半句为真，后半句为假——新位置上结论可能仍成立。出问题的条件：只要项目改过名/搬过盘（本项目已发生），L1 的**多数命中**就是误判。危害不是「多隔离了无所谓」：本项目的目标是「让后来者少走弯路」，把仍有效的结论（如「某文件某行有坑」）错误劝阻，后来者就会重新踩一遍坑——与项目目标直接相反。且 L3 那行写的「旧名路径整体失效」把这个错误语义说死了：旧名**引用**需要改写，不等于**结论**失效。
- **端口**：「端口无监听」探测的是**存活**不是**存在**。本机服务（ollama 等）不常驻是常态——服务没启动的那一刻去探测，「端口 11434 提供服务」这类结论就被误标失效。误报是常规路径，不是边角案例。
- **模型**：「模型不存在」对历史实测类结论（如「实测 prompt caching 降 90%」）不构成失效：那是历史记录，为真于当时；且模型消失后无人能照做，**自我消解**，反而是危险度最低的一类。把它算进失效是语义错位。
- **「88 条」的口径**：88 是「有可验证前提」的数量，不是「失效」的数量。真 🔴 的规模要在下面这个修法跑完才知道，文档应区分这两个口径。

**修法（基础设施已在，成本低）**：L1 对路径做三路判定——① dead-with-successor：用别名表（`ENTITIES` 里 demo-wiki→demo-kb 等，topics-a.md 已落地）把旧路径改写重指向新位置、重验，验不过降 🟡 带注；② dead-no-successor：真 🔴；③ alive：前提通过。端口改配置级检查（compose/启动脚本）或「连续 N 天无监听」；模型类结论不进失效判定，只做「无法照做」的降权提示。

## 二、值得改（7 条）

### W1. 反作用条件 3 存在空真问题，需要「索引水位」门

「没有后续会话推翻它」在索引未追上时空洞成立：4 个 agent 入库节奏不同、会话随时间持续追加。刚入库 Claude 的旧结论时，Codex 昨天写的推翻句可能尚未进索引 → 条件 3 误真。出问题条件：任何跨 agent 时间差场景（常态）。修法见 Q4 的水位迁移：断言条件 3 前，要求同（实体×意图）下晚于该会话结束时间的会话已全部入库。

### W2. 条件 2「文本仍显得权威（…肯定语气）」不可计算

路径/数字/端口是机械特征，「肯定语气」没有规则——三条件判据在条件 2 处断掉，要么落回人工、要么偷偷上 LLM（违反本仓「可复核」纪律）。修法：删「语气」，条件 2 = 存在具体路径/端口号/数值参数。附带好处：机械特征与 L1 载体高度重叠（只有 88 条带这些特征），「起反作用」桶自然收敛到小而有界的集合。

### W3. 两套「verified」概念冲突 + 🟢 档读法歧义

timeline 的 `verified`（关键词「实测/验证通过/跑通」，1295 条）是**自述实测**；处置档 🟢 写「前提有效 + 有实测」。两种读法都出问题：
- 强读法（前提须主动验证通过）：🟢 ⊆ 88 条，则 1295 条自述 verified 几乎全落进 🟡「未验证」——**同一条结论在时间线上标 verified、注入时标「未验证」**，用户必然困惑。且此读法下 🔴+🟢 ≤ 88（2.8%），三档实际退化为两档，应明示。
- 弱读法（未被 L1 标红即算前提有效）：🟢 ≈ 1295，但「前提有效」名不副实——只是「未发现失效」。

修法：改名区分「self-reported 实测」与「前提已验证」，并在设计里写出三档的期望分布，别让读者对绿灯规模产生错误期待。

### W4. verified 关键词集没过自家探针纪律

timeline-b §二 的方法论是：标记词必须先 probe——「修复」251 命中大多是菜单项、「确认」多为动作过程，都被实测杀掉了。「实测/验证通过/已验/跑通」这组词没做过同样检验：「跑通」在「跑不通」的否定语境、「你说实测过」的转述语境都会误命中。影响面：1295 条的纯度未知，而它恰是 🟢（弱读法）的门。修法：对这组词跑一次 `probe_conclusion_markers` 式抽验（本评审不执行，仅建议）。

### W5. 注入选择策略缺失，「隔离」没有生效面

🟡 3085 条「正常注入但标未验证」——上下文有限，不可能全注；选哪几条、按什么次序，设计没说。失效标记只是注入策略的**输入**，注入策略才是产品面；没有它，🔴「单列 ≤5 行」之外的整套分档不产生行为差异。出问题条件：第一次真实注入时。修法：至少给 🟡 定次序——新近优先、verified 关键词加权、**双 agent 交叉印证加权**（同一结论在 ≥2 个 agent 独立出现，可信度高于单源；这个信号在你的数据里现成：4 agent 618 会话，design.md 的表显示同一项目天然跨 agent 讨论）。

### W6. L4「只能人工」过于绝对——候选生成可以机械

L4 的**裁决**确实只能人工（天花板承认成立），但**候选生成**不用：实体×意图时间线已有（topics-a/timeline-b 落地），若同实体较晚会话出现「部署与性能/并发/扩展」类意图、而早前结论含「单机/够用/本地」字样，即可机械标「假设漂移候选」交人裁。不做的代价：97% 🟡 里属于 L4 的那部分永远无人发现——没有人会人工翻 3085 条。修法：加一条规则生成候选，人只做裁决；这与「不自动判失效」不矛盾，是自动**分诊**。

### W7. L1 判定无时间性

失效是「何时检验」的函数：路径删了又建回（git 恢复分支）、服务后来启动、盘符重挂——一次性标死的 🔴 永不复核就永久误标；反过来，缓存的 🟢 在前提死亡后也无感。出问题条件：检验时刻 ≠ 使用时刻（几乎总是）。修法：L1 结果带 `check_at` 时间戳；注入时**懒检验**（分析时探测、注入时复核），或定期重跑。

## 三、过度设计（4 条）

### O1. L3 作为独立层是冗余的（按现文）

表里写「已被 L1 覆盖」——被覆盖的层不该出现在分层表里，且这个说法混淆了「检测到」与「正确处置」（见 E1：L1 检测到了迁移幽灵，但处置错了）。修法：降级为 L1 **之前**的路径改写预处理（别名表已存在），或从分层表里删掉。

### O2. TOKI 双时态算子

本场景需要的全部时态信息是「结论产生时间 + 检验时间」两个字段。point-in-time 查询代数是为多用户、多版本知识库设计的；单人本地工具引入它是负资产（维护成本 > 收益）。W7 的 `check_at` 字段已覆盖真实需求。

### O3. PACMI 级联失效——不做是对的（Q2 详述）

列在这里是为了把「调研到但明确不做」显式归档为正确的过度设计规避，你的判断成立且可以更硬（见 Q2）。

### O4. MemGuard 式 verifier 信号持久化

本管线无 LLM、无外部 verifier；可持久化的信号只有 verified 状态与 L1 结果，两者已在设计内。为不存在的信号预建存储结构是过度设计。

## 五、对文档末尾 5 个问题的直接回答

**Q1：是否抓住主要矛盾？有没有根本性错误？**
主要矛盾抓对了（97% 天花板的承认 + 3% 机械层 + 不删但隔离，方向正确）。有一处根本性错误：**E1**——L1 的判定语义越界，且恰发生在自称「机械可信」的那一层，实测主流场景（迁移幽灵 58/76）正是它的误判区。另外「起反作用」三条件在 W1/W2 补齐之前不闭合（条件 2 不可计算、条件 3 空真）。

**Q2：级联失效值得做吗？你的判断对不对？**
对，且可以更硬。级联需要「结论→结论」的引用边；实测同键多值 = 0 说明这类边建不起来。再补一刀：即使 3% 有前提的那批，它们的前提是路径/端口/模型——**外部世界对象，不是其他结论**——连「前提→结论」之外的边型都不存在。L1 本身就是退化的单跳级联，而且是唯一存在的边型，你已经覆盖了。不做正确。

**Q3：三条件判据过硬吗？漏了什么反作用类型？**
不过硬，三处：条件 1 继承 E1 的语义问题；条件 2 不可计算（W2）；条件 3 空真（W1）。漏掉的反作用类型：
- **适用范围错配**（你自己举例的那类，确认存在）：三条件全过但结论属于另一个项目。实体覆盖 81%（topics-a 实测），且记录过 agent-memory 会话被误归「demo-kb」的真实案例；多实体会话 top-3 并列。注入时没有「结论所属项目 vs 目标项目」的匹配护栏。
- **矛盾对**：两条 🟡 互相冲突、无先后裁决地同时注入，比不注入更糟。同键冲突检出为 0 ⇒ 大多数冲突无标记。
- **verified 腐烂**：实测结论的验证本身过期（费率/行为变更），无前提可验 ⇒ **永久通过三条件**——判据没有老化项，这类反作用永远漏。

**Q4：阿里云 Tombstone + 版本水位怎么迁移？**
可迁移三件：
1. **「未被撤回 AND 索引已追上水位」的双条件引用资格**——直接补 W1 的洞。水位在本场景 = 每 agent 已入库会话的最大结束时间；断言条件 3 前，要求同话题更晚会话已全部入库。
2. **Tombstone 原因类型学**——映射 L1 原因 / L2 推翻 / L4 语义，给 🔴 注记现成的结构。
3. **「物理保留 vs 引用资格分离」**——你已暗合，显式成文即可。

不适用两件：
- **版本阶梯 / revision**：会话是 append-only 记录，无版本概念；「版本号」只能映射成「会话结束时间 / 入库批次」这种弱替代。
- **撤回的权威性**：阿里云的撤回是源系统的权威信号；会话里的「改为」只是**证据级**信号。同样的门，强度更弱——只能降权，不能裁决。这是本质差异，迁移时要降级预期。

digest 视 P3 而定：若会话会迟到追加，per-session digest 反而有用（检测漂移触发重入库）。

**Q5：明确不做的事，哪条做错了？**
三条里没有一条「做错」：
- **自动连演进链**：不做对——0 条同键多值是硬实测，链连不起来。
- **删除错误思路**：不做对——与「物理保留/引用资格分离」及本仓「只改标签不改原文」纪律一致。
- **LLM 生成台账**：不做台账对，但这条把两件事捆在一起扔掉了：①「不做 LLM 台账」（对）；②「🟡 不做任何次序」（**错，必须做**，见 W5）——否则「靠人确认 3085 条」在现实中等于永不确认。且 timeline-b §一.3 自己预留的折中（只在已定位候选上用 LLM 判推翻）不应被这条一刀切掉。
